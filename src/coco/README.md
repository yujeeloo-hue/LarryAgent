# Coco

Coco replaces Loops with an application-owned commander. It interprets chat goals, saves executable work and rule suggestions, dispatches ordinary Larry Agent project sessions, supervises their progress and questions, and verifies outcomes before reporting completion. It discovers evidence-backed follow-ups through ledgered wakes (task outcomes, workspace changes) and a configurable heartbeat, independently of Rules.

## Chat uses the existing Larry session and conversation UI

Coco Chat is a persistent `SessionStore` session (`source: coco_chat`). It runs the same `runAgentTurn`/TurnHost loop, provider adapters, transcript checkpoints, tool argument validation, tool-result feedback, compaction, cancellation and native questions/confirmations as an ordinary Larry conversation. The session ID and full message/tool history survive restarts. Legacy Coco messages are imported once as actual user/assistant messages; the internal conversation is omitted from ordinary project task lists.

The right-hand Chat area embeds the existing `ConversationController` and `ConversationView` in transcript-only mode. The navigation, central work pages and resizable right-hand column retain their existing layout. Chat is one rounded, bordered card without a title bar; its top aligns with the first panel below the page heading (the runtime panel on Overview), independently of work-page scrolling. The collapse control sits in the card's top-right corner. Unboxed messages and removable Discussing task context sit above a full-width footer that contains the prompt queue and composer, separated from the transcript by one divider rather than a second input card. These presentation overrides are scoped to CoCo. Message grouping, Markdown, Thinking, tool cards, ask-user panels, approvals, streaming, pagination, retry presentation and scrolling use the shared implementations. Coco routes its own send/stop/retry actions into the persistent commander session. It does not instantiate a second composer, model picker or Git footer.

Conversation text is never parsed as a task JSON document. Commander-only `coco_context`, `coco_work`, `coco_memory`, `coco_workspace` and `coco_balance` tools are injected for the trusted turn rather than registered globally or inherited by subagents. Submission arguments use a shared schema plus current project/session/DAG/domain validation; failures return through the ordinary tool loop so the model can correct them. Task and rule changes are saved transactionally. The assistant then replies naturally, including Markdown lists that previously failed with `No number after minus sign in JSON`. `coco_workspace` create registers projects on its own (mkdir when missing, idempotent, refuses non-empty non-git folders); those rows carry `origin:"coco"` for the sidebar mark. Submitted work starts immediately (full autonomy, 2026-11-04): only `planOnly` keeps drafts, and an automatic wake still cannot create or activate rules (`rulesDraft`).

Coco Chat reuses `PromptQueueView` and the ordinary composer's submit resolver. While an interactive reply is running, Enter with content queues a deferred prompt; empty-composer Enter arms the first deferred prompt for insertion after the current model/tool step. Rows support inline editing, move-to-front, removal, insertion and cancellation. Armed prompts merge at the native round boundary. A clean turn completion sends the next deferred prompt as a fresh commander job; Stop/error preserves the queue and disarms pending insertion. Idle rows offer Send now. Follow-ups re-enter CoCo's engine rather than starting an ordinary app turn, preserving commander tools, metering, scope and selected work references. Promoting during an automatic greeting starts interactive Chat with fresh access. Native question answers still resume their existing turn. Queue snapshots are session-scoped; late hydration/IPC replies cannot replay consumed rows after navigation. The Chat width defaults to 400px and retains the user's saved resize preference.

Coco domain messages are a compatibility/goal projection; the native session transcript remains authoritative. Background verification, reports and inspections still require structured results, and now support a result-submission tool and bounded correction when a provider returns prose instead. They do not expose raw JSON parser failures as conversational replies.

Run results use a flat, output-first layout: readable task reports, a dated progress timeline, then expandable acceptance details. Execution sessions receive a scoped `publish_coco_report` tool that saves complete Markdown or a project Markdown/text file (up to 256 KiB) as an immutable `workResult`, linked to the work revision and execution attempt. Publishing does not complete verification; saved report content is included in the independent review. Ordinary final replies and explicitly referenced project reports are also captured when execution finishes. Results load on demand through `coco:workResults`, keeping report bodies out of recurring snapshots and coordination context. Opening historical work can import its original execution reply and report files that have not changed since that attempt; it never scans for guessed filenames or substitutes later turns from a reused session. Saved outputs survive source-file changes and session history retention. The Reports page continues to contain consolidated daily reports.

## Home, persona and memory

Coco owns a private home at `{userData}/coco/`, stored as the reserved workspace `coco-home` (`COCO_HOME_WORKSPACE_ID`). `loadAllWorkspaces()` skips it, so it never appears in Projects, and it cannot be updated, archived, deleted, made active or used by ordinary sessions. Coco Chat sessions bind to the home instead of borrowing a project; a pre-existing Chat session bound to a project is replaced once by a new home session seeded from the recent Chat projection.

The home holds `AGENT.md`, `SOUL.md`, `COCO_MEMORY.md` and `COCO_AUTONOMOUS_EXEC_PROMPT.md`, seeded from `resources/prompts/coco/` when missing and re-read every model iteration. Persona files still byte-identical to the last default written (`.seeded.json`, plus known pre-record defaults) follow the shipped default on startup; edited copies are left alone (`readCocoPersona` → `resolvePersona`). The Chat prefix is Environment → Coco SOUL → USER → `[COCO_MEMORY]` → Coco AGENT → scenario prompt (commander / wake; autonomous wakes add `[AUTONOMOUS]`). The shared IDENTITY / SOUL and the home's PROJECT.md are not injected.

`COCO_MEMORY.md` has four sections — Projects, Focus, Open items, Work log — with a 10,000-character soft cap. `coco_memory` reads, updates (merge / replace per section; Work log bullets are timestamped) and searches the archive. Over the cap, an LLM rewrite (`coco/memory-consolidate.md`) is accepted only when it keeps all headings, fits the cap and keeps every live Open item; every bullet that leaves the file is archived verbatim as `coco_records` kind `memoryArchive`. Otherwise the oldest Work log entries, then closed Open items, then the oldest Focus entries are archived and trimmed until the body is at most 80% of the cap.

Coco Chat may write every non-excluded project directly. `read_project_memory` / `update_project_memory` accept `workspace_id` on Coco turns (`cocoProjectPath` capability) to target another in-scope project; other agents get an invalid-argument error. Coco-run execution sessions (`source: coco`) receive USER and PROJECT injection like ordinary sessions. A write (`write_file`, `patch` including V4A bodies, `convert_to_pdf`, `update_project_memory` with `workspace_id`) or a Shell command naming a project root is refused with a recoverable tool error while that project has an active turn; Coco then steers or appends into that session.

## Permissions and settings

Coco uses **Full permissions** and Larry Agent's existing model, Shell and MCP configuration. There is no second Shell opt-in, network-host list, runtime directory list, MCP grant table or session exclusion list. Persisted obsolete permission fields are discarded when settings are loaded. In Coco Chat itself, ordinary Larry Agent tool permissions and explicit Ask/risk confirmations still go to the user.

Supervised sessions — CoCo execution turns and handed-over (`source: coco`) sessions once supervision is live — run with Full permissions through live gate getters, so a mid-turn hand-over or take-back applies to the rest of that turn. They also get high-risk review: Shell Safe Mode Class B findings (force push, `sudo`, `git reset --hard`, outside writes, …) still confirm under Bypass, and `write_file` / `patch` into a sensitive credential or system path confirms (the OS temp directory is excluded). Every confirmation there — per-tool Ask, Shell risk or Hook `ask`, tagged with its `source` — goes to the decide model first (`toolApproval.ts` builds the question with the risk reason, Trash note, saved goal and clipped arguments). Approve runs the tool; Deny returns a denial and the turn continues; needs_user or a failed decision goes to the user (hand-over: the parked CoCo Chat card; execution: To decide with approved replay). Fatal Shell findings never reach the model and always go to the user; Safe Mode `block` stays blocked. Every verdict is recorded as a `supervision` record.

Settings → Coco contains enable/disable, default model, an optional **Decision & verification model** (`fastProviderId`; empty = default model), hourly/daily token budgets, daily report time, conversation retention, optional **Context compaction** overrides and **Excluded projects**. The Context compaction section independently sets the compact trigger ratio (`compactTriggerRatio`, 0.5–0.95) and keep/protect token ratio (`iterationProtectTokenRatio`, (0, 0.9] — the same knobs as the Agent settings) for CoCo Chat conversations; switched off, Chat follows the global Agent settings. Execution and internal background lanes always use the global Agent knobs, and the session-end full digest is unaffected. Context compaction is separate from the History retention setting. Rules are managed in the Rules area. Inspection (15 minutes), event coalescing (30 seconds) and repair limit (3 rounds) are internal defaults.

Global project exclusions apply to context discovery, session/history tools, file paths, known MCP path arguments and Shell. File checks use canonical and lexical paths, including symlinks. Full permissions permits ordinary paths outside the assigned project directory; the cwd is not a second read/write boundary. Execution sessions touch only their own project: every other workspace path — excluded or merely another project covered by the same rules — is denied for file tools, known MCP path arguments and Shell, so multi-project goals run as one work item (and one project session) per project, with cross-project facts inlined into each objective. A failed planning read is returned to the model with a recoverable error and audited, rather than terminating the entire chat. Actual project roots are included with summaries.

Shell calls use the shared executor and normal environment/network behavior. Coco owns their cancellation and process-group cleanup. On macOS, configured excluded roots are additionally denied by an automatically generated process profile. On other platforms, Shell works normally without exclusions; nonempty exclusions fail closed until a platform backend is implemented. This macOS implementation is not a claim of containment against arbitrary daemonization or all other tool transports.

MCP calls use the existing connected `mcpManager`; configuration, credentials and server lifecycle stay in Larry Agent. Known file arguments are checked locally, but an opaque external MCP server operates with its configured service permissions. Local project exclusions cannot prove that a third-party service will never access related external data. There is no separate Coco grant configuration or private MCP connection.

## Background operations reuse native Sessions

Planning, inspection, verification, supervisory decisions, recovery review and reports now run through the same persisted `SessionStore` / TurnHost as Chat and project execution. They use independent internal sessions (`source: coco_internal`), per-turn scoped read/result tools, native checkpoints, normal tool feedback, native automatic compaction and metered model/summary calls. Internal sessions are omitted from project task lists and require a main-process background capability to resume; raw IPC cannot claim them. The saved operation ID reuses its session across retries/reopen, while exclusion-context changes use a new session.

CoCo Chat shows these operations as task cards with live native reasoning, expandable tool arguments/results, final summaries and retained history. Their model contexts remain independent from interactive Chat, which can reply during recovery or planning. Card snapshots contain metadata only; transcripts load on expansion in read-only mode. Current project exclusions and context revocation also apply to visible history.

Background turns advertise only their scoped evidence/context readers and structured-result tool. Recovery and acceptance can request fresh project evidence through the scoped reader; ordinary execution tools are neither offered nor allowed. Provider replay envelopes remain saved for continuation but are omitted from review evidence. Recovery checks time out after five minutes and retain the existing three-attempt limit across application restarts. Failure or exhaustion becomes an explicit retry/decision state, rather than an orphan running check.

The former 500,000-character rejection and separate background model/tool loop have been removed. Large operation inputs are stored in full; a bounded preview and `coco_job_input` expose field/index/offset pagination, including the final page. Large context reads use the same paging path. This is input retrieval, not a second context-compaction implementation: growing transcripts use the existing native compaction strategy. Canonical tasks, criteria, permissions and fresh evidence remain owned by Coco's domain layer. Background read/result tools cannot execute arbitrary project mutations.

Context-capacity failures are automatic runtime retries with persisted backoff (30 seconds increasing to 15 minutes), never To decide and never a reason to replay already finished execution. A failed verification retries verification; a pending supervisory question retains its request. At startup, the exact legacy context-limit decision is automatically returned to verification or interruption recovery. App shutdown, global disable, exclusions and automation token budgets still apply.

## Commander and session execution

The runtime has four independent admission lanes: interactive native Chat, supervisory decisions, background coordination (goal planning, inspection, verification and reports), and task execution. Decisions block a live execution, so they never queue behind coordination work. Within coordination, verification ranks ahead of inspections and reports. A task or long planning request cannot put Chat behind the task queue, and Chat does not preempt or force an executor to yield. Successive turns of the same Chat remain ordered. Tasks in the same project run one at a time while one is executing, recovering, being verified, paused, or waiting on To decide. A task that is only watching a user turn yields that project. Tasks in different projects run at the same time, because they do not share files. This does not stop unrelated sessions the user was already running.

`coco_work` action `plan` durably accepts a goal and returns immediately so the user can keep talking while decomposition runs. Planning results enter the work queue and are delivered to the same native Chat through an idempotent outbox. A notice waits for any current native turn to finish, preserving tool-call/result ordering. The Overview shows pending planning requests and supports cancellation. Small, already specified plans can still be saved directly with `coco_work` action `submit`; `cancel_planning` cancels a pending request. In Chat, `update_rule` (partial patch merged onto the rule), `pause_rule`, `resume_rule` and `delete_rule` change existing rules through the same `rule` command as the panel (validation, scope checks, aborting affected work); existing rules are listed in the Chat context and the `coco_context` overview. Autonomous wakes cannot change rules. Enter submits the composer, Shift+Enter adds a line, and IME confirmation never sends the draft. A draft typed while submission is acknowledged is preserved.

Planning reviews project/session summaries first, then audited relevant transcript/file reads. All non-excluded session origins are visible, including Coco-created sessions. The structured plan can specify:

- `executionSessionId` with `sessionStrategy: "continue" | "steer" | "append"` to reuse a related project session.
- `observeSessionId` to watch without delivering instructions.
- No session reference when a new session is needed.

References are validated against accessible session IDs and their workspace ownership. The model selects semantic relevance; exact-title matching is only a fallback. Work linked to the same session merges goals, source rules, requirements, steps, dependencies, deliverables and acceptance criteria. New requirements increment the revision; prior verification cannot approve that new revision. Merged dependency cycles are rejected transactionally. Paused/cancelled sessions need an explicit resume; a planner cannot silently undo the user's stop.

Steer uses the existing armed prompt queue and is consumed at a natural model/tool boundary, without aborting the current request or tool. Append starts a later turn in the same session. Idle sessions continue directly. Process-local capability mappings keep trusted execution IDs out of public queue records and IPC. A queued project-execution Coco turn remains metered and scoped; cancellation removes Coco's pending messages and cancels its owned turn, while leaving an original user-owned turn alive. A user can open and continue a Coco-created project session normally.

An attached supervisor handles ordinary `ask_user` questions through a structured, metered commander decision. The decision is a single low-reasoning-effort request (`cocoDecide.ts`) on the decision model, not a background session: its input is the session's model-facing conversation with thinking and tool calls removed: the rolling summary, user prompts, and assistant reply text, plus the question and its options. It does not page for more. A reply that is not valid JSON, or no reply within 60 seconds, becomes To decide. It defaults to answering: technical, design and ordinary product choices are resolved from the summary, user prompts and assistant replies (preferring reversible, minimal-scope options and stating any assumption), and it records the question, answer, rationale, revision and session. Only unauthorized irreversible/destructive actions, credential or access requests, choices contradicting an explicit requirement or the goal, and questions with no justifiable option become To decide. The execution turn stays parked on that ask_user call; the user's choice is written into the tool result and the same turn continues. Explicit tool confirmation still records exact arguments for a one-time, revision/configuration-bound replay through the existing tool checkpoint pipeline. Recoverable Shell/MCP tool failures return to the execution agent; unknown external effects require review before replay.

## Hand-over supervision

A session handed over from the sidebar (or any `source: coco` session the user keeps talking to) is tracked as observed work (`CocoEngine.watchSession`, `work.handover`). The work waits while the session's turn runs; when it finishes, the same verification decides complete / continue / needs_user against a fixed hand-over goal (`HANDOVER_OBJECTIVE`: the user's request in that conversation; a reply that stops to ask for review or confirmation of a reversible step counts as not done). `continue` sends the short prompt into the same session, keeping the session's own provider, run mode and reasoning effort; the repair limit and repeat-prompt guard apply. Every later completed turn of a CoCo-managed session with no open work starts a new watch (`done` stream events in `cocoService`). Take-back cancels the hand-over work (`releaseSession`). The Chat hand-over turn only reports the session's state; it does not steer or append itself.

## Conversation retention

Settings → Coco includes **Conversation retention**, default **30 days** (also 90 days or Keep all details). Retention is separate from native model-context compaction. A low-priority daily cleanup runs only while Coco/the application are enabled and within automation budgets. It summarizes expired whole turns of Coco Chat and completed internal background sessions, then physically replaces their detailed message rows with a native summary marker and keeps recent turns. Ordinary project sessions, project files, task links, criteria, reports and verification evidence remain.

Active turns, pending questions/approvals/prompts, unresolved effects, excluded scope and unfinished work protect their history. The summary is generated in an ordinary native background Session. For paged retention input, the backend requires complete source-read coverage before accepting the summary. Empty/failed/incomplete summaries preserve the source. A digest check prevents a stale rewrite when messages change during summarization. Completed summaries survive database reopen; an open conversation refreshes after cleanup. Expired compatibility message bodies and background input snapshots are cleared as well. Temporary retention-analysis copies are reduced to summary/status, including recovery after an interrupted cleanup.

## Completion, budgets and lifecycle

A finished session turn is evaluated by the decision model. The user message is plain text: the task, the rolling summary, and user and assistant replies, with thinking and tool calls removed. Only the evaluator's reply is JSON. The evaluator can list directories, read files, and search text with read_coco_context. complete finishes the work. continue sends only the evaluator's short prompt into the same session for another turn. needs_user becomes To decide, and the user's answer is that next prompt. Basic and low-to-medium-risk choices are made by the evaluator. Default continuation limit is three rounds, stopping earlier when the same prompt is repeated. Uncertain external effects are not advanced automatically.

Hourly/daily token totals use natural windows in the configured timezone. Every Coco model request is metered and counted toward them, including supervision, compaction and interactive Chat; Chat turns can therefore trip the automation cooldown too. With Coco enabled, Chat itself stays available during automatic-work cooldown and uses ordinary Larry Agent/provider limits. The master enable switch still stops both Chat and automation. An original user-owned turn remains user usage; steering it does not retroactively reattribute its earlier requests. Active turns finish before cooldown. A deferred new Coco turn cannot bypass an exhausted budget; its saved requirements return to the queue. Overview → Reset budget clears the current hour and day totals (Chat included) immediately and continues queued work. Quit or access revocation cancels immediately.

The service and file/Git observations run only while Larry Agent is alive. Closing a window can leave the app resident; fully quitting stops admission, requests and owned execution. No Coco LaunchAgent, daemon or macOS task scheduler is installed. Shutdown cleanup is bounded. Startup skips missed schedules, recovers already accepted interrupted work, and queues a lightweight review after eight seconds once enabled. A durable main-process turn journal distinguishes connection/crash interruption from explicit user Stop/Pause. A clear abnormal interruption resumes the same session with the user message `Continue` and does not call the recovery model. The recovery model remains only when that journal cannot classify the interruption. That call receives the same plain-text task, summary, and user and assistant replies used for verification. Only its reply is JSON. Recovery uses a bounded backoff and at most three attempts; counts survive restart. Explicit user Stop/Pause stays waiting until resumed. Unknown external effects cannot be replayed automatically; they go straight to To decide. Legacy retirement is verified before starting Coco; transient retirement errors retry while keeping execution blocked.

Domain records, dispatch admissions, model usage, supervisory decisions, attempts and verification live alongside sessions in SQLite. Queue capability tokens exist only in memory. Restart does not blindly replay a possibly consumed steer. Loops migrate idempotently to fixed rules with original settings/history preserved in `legacyConfig`; effective Coco permissions follow the new Full-permissions contract. Rules that support delegated goals activate immediately. Explicit previews stay drafts, and user-paused rules stay paused.

## Validation boundaries

Tests use isolated temporary projects, local provider-protocol/MCP fixtures and the real SessionStore/tool pipeline. Coverage includes concurrent intake with per-project work execution, existing-session steer/append, no interruption of active user requests, revocation, cooldown, automatic technical answers, merged acceptance revisions, recoverable context failures, excluded paths, shared Shell/MCP, typed confirmation, fresh verification, migration and startup recovery.

Renderer checks use the actual components with sample data; they do not run the user's live tasks. Passing local tests/builds does not constitute packaged Windows/macOS acceptance, external-provider acceptance or proof of arbitrary MCP-server behavior.

## Rule scheduling, stale sessions and recent runs

Interval ("every N minutes") rules keep their phase across restarts: a pending `nextRunAt` survives startup, and occurrences missed while the app was closed are skipped to the next slot on the original cadence rather than restarting the countdown. Calendar cadences are unchanged.

A plan that names an execution session which no longer exists (deleted or out of scope) drops that link and runs in a new project session instead of rejecting the whole plan; model input omits such stale `sessionId`s. Queued work whose linked session was deleted or archived also starts a new session; archived sessions are not offered to the model as context. A session that moved to another project still fails. Optional plan fields sent as `null` (e.g. `deadlineAt`) are treated as absent.

CoCo's own planning / inspection / verification turns run in `coco_internal` sessions, which never appear in the Projects list by design; only execution sessions (`source: coco`) do.

A failed rule run retries the same run after 1, 5 and 15 minutes (transport, structured-result and plan-validation failures); only the final failure posts a Chat message. A fixed rule that legitimately produces no work is not retried.

Every rule run is recorded (`ruleRun`, last 100 kept) with status, attempts, CoCo's summary and the planned work. Chat requests that planned work also appear as runs (`source: "chat"`, derived at snapshot time from the user message, CoCo's reply and the work whose `goalIds` include it — not stored): they stay in progress while that work is queued or executing, and once all of it is finished they show as Completed at the completion time (rule runs stay at their trigger time). Overview → **Recent runs** presents a timeline: running/retrying runs stay visible at the top, followed by recent history grouped by date in the configured timezone. Five records are shown initially (all active records remain visible); older records from the current snapshot can be revealed locally. Each record previews a plain-text summary and task outcomes; expanding it reveals the complete Markdown summary, any failure/retry error, and task acceptance from the latest verification. Task rows open the existing work detail. Expansion and the older-record toggle survive snapshot updates.

Overview cards below the runtime banner use a fixed order (`overviewOrder.ts`): To decide → Planning → Moving forward (in-progress work, then queued work and today's scheduled rule runs) → Latest report → Recent runs. Cards with no content are hidden; shells collapse/fade in and out. Latest report is a compact, fully clickable daily-report cover: an English month/day in the configured CoCo timezone, "Latest report", "Daily work report", and a 16px highlight triangle at the top-right corner when unread. The corner and navigation arrow use the app accent. Its solid, subtly tinted background follows the app accent; it omits the excerpt, author and time. Clicking anywhere opens Reports and marks the report as seen (renderer-local `coco.reportsSeenAt`, at most one day), removing the corner marker. The report's saved title and content remain available on the Reports page.

## Project awareness

`createCocoAwareness` (`src/main/cocoAwareness.ts`) keeps `COCO_MEMORY.md` Projects in step with every in-scope project. It syncs at start, on workspace lifecycle events and on scope changes, and listens to `onProjectMemoryWritten`, which fires for every programmatic PROJECT.md write (`update_project_memory`, post-turn extract, `setProjectMemoryBody`). Records: `projectTask` (pending work per project: `onboard` on the first enable, `added` afterwards, `changed` for PROJECT.md updates) and `projectDigest` (hash, one-line index entry, summary, last meaningful change). Writes are debounced 60 s per project and skipped when the content hash is unchanged; the first sync after start also re-hashes files edited while the app was closed. Removed or excluded projects leave memory.

The engine runs ready tasks as a `project` job on the coordination lane (shared budgets, cooldown and metering, 2-minute slices). A documented project gets one reasoning-free digest call (`coco/project-digest.md`, fast provider) with a deterministic Basics fallback. A non-empty project without PROJECT.md (or with only the template) gets a read-only background analysis (`coco/project-analyze.md`, `read_coco_context`) that writes its first PROJECT.md; this is deferred while the project has an active turn. Empty projects are recorded as empty. Onboarding and new projects are announced in Chat; meaningful changes go to the Work log. Failures back off 1 / 5 / 15 minutes and then drop. `createCocoService(..., { projectAwareness: false })` disables it (integration tests).

## Autonomous wakes

Plan: `docs/plans/20261102-coco-wake-autonomy.md`. Wakes are driven only by recorded facts; nothing is polled.

- **Wake ledger** (`wakeLedger.ts`, record kind `wakeEntry`): `project_doc` (PROJECT.md / `docs/WORKLOG.md` writes via `onProjectMemoryWritten`, `onProjectWorklogWritten` and tool file writes), `work_status` (task completed; failed = every `to_decide` except a live `ask_user` escalation, including retries exhausted; interrupted by app restart) and `workspace_added` / `workspace_removed`. Ordinary sessions and user stops are not ledgered. Entries are recorded only while CoCo is enabled; delivered entries are pruned after 7 days.
- **Triggers**: task / workspace entries wake after a 3 s coalesce. Document entries and VCS changes wait for the heartbeat (`heartbeatMinutes`, default 15, 1–240). Git (`branch → commit`) / SVN (revision) are read only at heartbeat and wake time and compared with the `vcsBaseline` meta; external changes count.
- **Turn**: an `autonomous` job is a commander turn on the conversational lane. Prefix adds `[AUTONOMOUS]` from the home's `COCO_AUTONOMOUS_EXEC_PROMPT.md` (self-editable; Setting → Reset autonomous instructions) after AGENT, without the workspace line or Turn handoff. The briefing (all merged reasons, since time, Projects / Tasks / Workspaces) is the trailing wire-only note; no user message is created. Task lines carry `workspaceId` / `workId` for `coco_context` and merges. Plan / FSM / hand-off tools, `request_full_permissions` and `ask_user` are neither offered nor executable (a blocking question would hold the Chat lane); questions go into the reply plus a `[decide]` Open item. `coco_work` offers only `submit`. The wire carries only the newest 3 Chat turns (`conversationTurnLimit`; COCO_MEMORY and the briefing carry the rest). Automatic turns write no user message, so their first message ids (`chatTurnStartIds`) count as turn starts. While that window stays under the compact trigger, compaction is skipped and hard-truncate uses the local window estimate, since provider usage from the full transcript does not apply. Once the newest turns alone cross the trigger (one long wake), the iteration falls back to the ordinary compacted full window, so the turn limit never disables compaction. Iteration-protect compaction also summarizes iterations that precede the first user message, and keeps covered ones off the wire. New work and rule suggestions become drafts; inspection guards apply. Entries are marked delivered (and the VCS baseline advanced) only when the turn completes; a failed / stopped turn redelivers them on the next wake.
- **Heartbeat with nothing new**: when no work is active, queues one light small-talk remark through the visit greeting path (waits out the small-talk interval; an unanswered remark is not followed by another).
- User Chat queues behind a running autonomous turn (it only preempts greetings). Rules run on their schedule only; the `checkin` mode and rule event triggers are retired (legacy check-in rules load as paused inspections).

## Visits and recent Chat

Goal-related Rules are saved enabled without a second confirmation. Chat and background prompts distinguish delegation from discussion/preview requests. Rules retain origin and goal references; plan-only rules retain a draft marker. Legacy unconfirmed Rules are reviewed against original delegation and can be activated only if it is clear; explicitly marked drafts and user-paused Rules cannot be auto-activated. Automatic repeated suggestions do not replace an existing equivalent Rule.

Mounting the CoCo page sends a visit wake once it is ready. A brief read-only greeting streams directly into the persistent native Chat, reporting current work stages and live session progress, pending decisions, or natural small talk while idle. It does not create a structured background operation or a task card. Its native turn suppresses user-message creation. Automatic remarks use a reasoning-off, text-only provider stream and the supplied concise status snapshot, without tools or further investigation. The visit prefix is lean (no workspace line / Turn handoff) and carries only `wake.md`; the status snapshot rides the trailing wire-only note (without a copy of recent Chat, which is already on the wire).
